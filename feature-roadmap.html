01 / 08

Golden Output Test Runner

Save an approved generated file as the expected result, then rerun and diff it after every template change.

Core delivered 0.1.0High impactMedium effort

Why it belongsGeneration without repeatable verification still leaves teams checking output by hand. JetForge already has generation, snapshots, diffs, compiler commands, and workspace validation—the difficult primitives are present.

Original four-step implementation plan
  1. Define a small workspace format such as .jetforge/tests.json that maps a template, compiler profile, and expected output.
  2. Add “Create Golden Test From Current Output” and “Run Template Test” commands with inline diff results.
  3. Expose the suite through VS Code’s native Testing API with pass, fail, duration, and diagnostic locations.
  4. Add a headless runner contract so the exact same tests can become a CI quality gate.

02 / 08

Generated Output Provenance Lens

Show where every preview line came from: root template, include, expression, skeleton token, or unmapped compiler output.

Delivered 0.0.22High impactMedium effort

Why it belongsSynchronized reveal currently answers “where did this line come from?” one selection at a time. A persistent provenance gutter would make unfamiliar generated code readable at a glance and turn source-map uncertainty into honest, visible information.

Original four-step implementation plan
  1. Extend preview source maps with a provenance kind and confidence: direct, include-expanded, skeleton-rendered, approximate, or unmapped.
  2. Add compact gutter markers and hover text to generated preview documents; use shape as well as color.
  3. Add “Show Source for This Output Line” and “Show All Contributions” for composite regions.
  4. Offer an optional heatmap overview that highlights reliable and ambiguous sections without changing the generated file.

03 / 08

Workspace Doctor

One command that explains what JetForge understands, what is missing, and the exact next action to improve the workspace.

Core delivered 0.1.0Medium impactSmall effort

Why it belongsJetForge has powerful settings for resolution paths, compiler commands, language modes, trust, and optional IP-XACT behavior. A project can be “mostly working” without making the missing piece obvious.

Original four-step implementation plan
  1. Run read-only checks for template detection, includes, skeletons, output directories, compiler placeholders, Java tooling, and Workspace Trust.
  2. Present results in a lightweight report with clear status, evidence, and no generic warnings.
  3. Attach focused actions: open the exact setting, create a safe default folder, test a compiler, or open an unresolved reference.
  4. Add “Copy Diagnostic Summary” for bug reports while excluding template content and local secrets.
MVP proofFive checks with direct fixes
Builds onToolchain checks + workspace model
GuardrailRead-only unless action is explicit
04 / 08

Interactive Dependency Map

A navigable local map of templates, includes, skeletons, classes, generated outputs, and unresolved edges.

Delivered 0.1.0High impactMedium effort

Why it belongsThe existing impact graph proves the data is useful. Interaction would make it operational: isolate the blast radius of one file, find dependency hubs, jump to unresolved edges, and understand large legacy projects faster.

Original four-step implementation plan
  1. Expose a stable graph model from the existing workspace index with typed nodes and edges.
  2. Build a local-only webview with pan, zoom, keyboard navigation, search, and “focus on this file.”
  3. Add filters for includes, skeletons, workspace classes, generated targets, and unresolved edges.
  4. Open source ranges from nodes and show transitive dependents before a rename, move, or deletion.

05 / 08

Refactor Preview & Safe Recipes

Show the exact files, references, and generated outputs a refactor will change before applying it.

Core delivered 0.1.0High impactLarge effort

Why it belongsJetForge already fails closed for include extraction and reference moves. A visual change plan would make that safety legible—and create room for higher-value recipes such as class renames, helper extraction, and import cleanup.

Original four-step implementation plan
  1. Create a reusable refactor plan model containing edits, file operations, unresolved blockers, and affected outputs.
  2. Preview the plan as a multi-file diff before calling WorkspaceEdit.
  3. Add one recipe at a time: rename an @jet class, extract a declaration helper, then organize directive imports.
  4. Optionally run affected golden tests after application and offer a single undo path if verification fails.

Builds onWorkspaceEdit + impact topology

06 / 08

Headless JetForge

A small CLI that runs workspace checks, compiler validation, and golden tests without launching VS Code.

Core delivered 0.1.0Very high impactLarge effort

Why it belongsEditor tooling catches problems while one person is working. A headless runner makes JetForge useful to the whole team on every pull request and gives projects a repeatable definition of “the templates are healthy.”

Original four-step implementation plan
  1. Extract VS Code-independent scanning, workspace modeling, generation, and diagnostic code behind narrow adapters.
  2. Ship jetforge check, jetforge test, and jetforge graph with human-readable and JSON output.
  3. Use the same workspace configuration format and compiler security rules as the extension.
  4. Provide copyable GitHub Actions and generic CI examples, but keep the runner vendor-neutral.

Builds onPure TypeScript model modules
GuardrailZero runtime network dependency
07 / 08

Fixture-Driven Live Evaluation

Choose a named model fixture and see the real rendered artifact—not only placeholder expressions—in the side-by-side preview.

Core delivered 0.1.0Very high impactVery large effort

Why it belongsThis is the most exciting leap: template authors could iterate against realistic scenarios without leaving the editor. It would make previews useful for content correctness, edge cases, and visual output—not just structure.

Original four-step implementation plan
  1. Start with user-configured external compiler profiles; do not attempt to interpret Java or bundle an Eclipse JET runtime.
  2. Define named fixtures as project-owned files plus a compiler command that knows how to load them.
  3. Add a fixture picker, cancellable generation, cached results, and explicit trust boundaries.
  4. Compare fixtures side by side and promote a rendered result directly into a golden output test.
MVP proofTwo fixtures, two real outputs
Depends onCompiler profiles + golden tests
GuardrailNo in-extension Java execution
08 / 08

IP-XACT Schema Intelligence

Optional schema-aware completions, validation explanations, and navigation for generated IP-XACT structures.

Delivered 0.0.22Medium impactVery large effort

Why it belongsJetForge already owns the template-to-XML boundary. Schema intelligence would create a strong specialist advantage for hardware teams while remaining safely opt-in for everyone else.

Original four-step implementation plan
  1. Support a user-selected local IEEE 1685 schema bundle; do not download schemas at runtime.
  2. Parse generated XML into a lightweight structural index and map reliable nodes back through template provenance.
  3. Offer context-aware element and attribute suggestions in matched generated-output regions.
  4. Add semantic navigation for components, bus interfaces, address blocks, registers, and referenced definitions.
MVP proofSchema error mapped to source
Depends onProvenance lens + opt-in IP-XACT
GuardrailDisabled means zero extra work

The sequence that got it shipped.

Each phase produced visible user value and lowered the risk of the next. The system remains local-first and needs neither a full parser nor a cloud service.

Phase 1 · confidence

Prove what exists

  1. Golden output tests
  2. Provenance lens
  3. Workspace doctor

Phase 2 · scale

Make projects safer

  1. Interactive dependency map
  2. Refactor preview
  3. Headless CI runner

Phase 3 · differentiation

Do what editors cannot

  1. Fixture-driven evaluation
  2. Schema-aware IP-XACT tooling

Keep these constraints. They are the product.

01

Truth over magic

Show mapping confidence and unresolved state. Never attach a precise-looking result to an uncertain source range.

02

Local by default

Templates, fixtures, compiler output, and diagnostics stay on the machine unless a project explicitly moves them.

03

Visible editor value

Every release should produce a behavior someone can see and use in VS Code—not only internal architecture.
